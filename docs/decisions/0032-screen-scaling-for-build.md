# 0032. 배포 빌드를 위한 화면 대응

- 날짜: 2026-09-06 (D10)
- 상태: 채택
- 관련: 0019(`~Screen` 부착 위치), 0028(HUD 구성), 0030(측정 환경)

## 맥락

WebGL 배포를 준비하며 작은 창으로 빌드를 실행하자 화면이 무너졌다.
에디터의 Game 뷰(1920×1080 고정)에서는 한 번도 보이지 않던 문제였다.

- 남은 시간 `4:50`이 **한 글자씩 세로로 줄바꿈**되고 화면 오른쪽 위로 밀렸다
- 레벨업 카드의 한글이 **네모(`■■ ■■`)로 뭉갰다**
- 카드 세 장이 화면을 거의 덮었다

브라우저 창 크기는 사용자마다 다르므로, 배포 전에 반드시 해결해야 하는 문제다.

## 결정

### 1. Canvas Scaler를 `Scale With Screen Size`로 전환한다

기존 `Constant Pixel Size`는 창이 작아져도 **글자의 픽셀 크기를 유지**한다.
반면 RectTransform의 폭은 창에 비례해 줄어든다.
그래서 폭이 글자 하나만큼으로 좁아지는 순간 강제 줄바꿈이 걸렸다.
시간 텍스트가 세로로 흐른 것이 이 현상이다.

| 항목 | 값 |
|---|---|
| UI Scale Mode | Scale With Screen Size |
| Reference Resolution | 1920 × 1080 |
| Screen Match Mode | Match Width Or Height |
| Match | 0.5 |

Match를 0.5로 둔 것은 가로·세로 어느 쪽으로 비율이 치우쳐도
한쪽만 극단적으로 잘리지 않게 하기 위해서다.

**한글이 네모로 보인 것은 폰트 문제가 아니었다.**
큰 창에서는 정상 출력되므로 글리프는 폰트 에셋에 들어 있다.
글자가 작아지면서 SDF 아틀라스 해상도가 부족해 뭉갠 것이며,
Scaler 전환으로 글자 크기가 창에 비례하게 되면서 함께 해소됐다.

> 12편에서 "작업 화면에서 크기를 비교하는 것 자체가 의미가 없었다"고 정리했는데,
> 이번에는 반대쪽이었다. **작업 화면에서는 멀쩡한데 실제로 깨지는 조건이 따로 있었다.**
> Game 뷰 해상도를 바꿔보지 않으면 드러나지 않는다.

### 2. Main Camera Orthographic Size를 8로 조정한다

기존 값에서는 플레이어 캡슐이 화면 세로의 상당 부분을 차지해
주변 상황을 읽기 어려웠다.

**판단 기준은 "캐릭터와 좀비가 함께 잘 보이는가"이며, 이 기준에는 수치가 없다.**
5 / 8 / 12를 직접 확인하고 육안으로 8을 택했다.
`spec.md`에서 대시 거리·쿨다운을 범위로 남기고 "테스트로 확정한다"고 쓴 것과 같은 성격이다.

**스폰이 화면 밖에서 일어나는지 확인했다.**
`spec.md`는 "플레이어 화면 밖에서 다가오도록 설계"를 요구한다.
`_spawnRadius`가 20이고 Size 8이면 세로 ±8 / 가로 ±14(16:9) 이므로,
Scene 뷰에서 카메라 프러스텀이 스폰 원 안에 완전히 들어감을 확인했다.
**Size를 더 키울 경우 이 전제가 깨지므로, 20 근처가 상한이다.**

### 3. 조작 안내를 HUD에 상시 표시한다

배포판에는 조작을 설명해 줄 사람이 없다.
README를 읽지 않고 링크로 바로 들어오는 경로를 전제해야 한다.
이동 / 대시 / 공격 방향 / 성장 선택 네 가지를 화면 좌하단에 고정 표시한다.

## 대가

- Reference Resolution 기준이 생겼으므로, 이후 UI를 추가할 때
  **에디터 Game 뷰를 1920×1080으로 두고 작업**해야 의도한 크기가 나온다
- 카메라 Size가 커져 화면에 그려지는 좀비 수가 늘었다.
  0030의 성능 측정은 전부 변경 **전** 값으로 수행됐으므로 표끼리의 비교는 유효하지만,
  이후 재측정 시에는 이 표와 직접 비교할 수 없다.
  다만 1차 기준 렌더링 비중이 0.84ms로 물리(10.60ms)의 8% 수준이라
  결론이 뒤집힐 가능성은 낮다

## 검증 방법

Game 뷰 해상도를 16:9 / 4:3 / 640×360으로 바꿔가며 확인한다.
빌드 없이 에디터에서 재현되므로, 배포 전 점검 항목으로 남긴다.

`gh-pages` 배포 절차는 **선택지가 있는 결정이 아니라 GitHub Pages의 제약**이므로
이 문서가 아니라 README의 실행/배포 항목에 기록한다.
