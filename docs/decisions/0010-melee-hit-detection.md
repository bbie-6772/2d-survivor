# 0010. 근접 공격 판정은 즉시 범위 판정으로 하고, 조준 입력을 분리한다

- 날짜: 2026-08-30 (D3)
- 상태: 채택

## 맥락

기획서상 몽둥이는 "플레이어 앞 부채꼴 근접 공격"이고 공격은 자동으로 진행된다.
판정 구현 방식이 셋이었다.

| 방식 | 내용 |
|---|---|
| (a) 즉시 범위 판정 | `Physics2D.OverlapCircleAll` 등으로 그 순간 판정 |
| (b) 투사체 | 프리팹을 날려 충돌 시 판정 |
| (c) 애니메이션 콜라이더 | 공격 클립 구간에만 켜지는 자식 콜라이더 |

초기 선호는 (c)였다.

## 결정

**(a) 즉시 범위 판정**을 채택한다. 원으로 후보를 모은 뒤 내적으로 부채꼴을 필터링한다.
조준 방향은 `PlayerAim`이 소유하고, 무기는 읽어간다.

## 이유

### (c)를 보류한 근거

- 애니메이션 클립 + Animation Event + 애니메이터 상태 동기화가 필요하다.
  **에디터 작업 비중이 큰 일**이며 마감(9/7) 대비 위험하고, 포트폴리오에서 프로그래밍 역량으로 드러나지도 않는다.
- 자동 발사와 궁합이 나쁘다. (c)는 애니메이션 재생 시간이 판정 타이밍을 결정하므로
  **공격속도 스탯이 오르면 클립 속도까지 조율**해야 하고, 무기 3종이면 그 조율이 세 배가 된다.
- (a) → (c) 전환은 판정 함수를 두고 호출 시점만 Animation Event로 옮기면 되므로 싸다. 역방향은 비싸다.

### 부채꼴을 내적으로 판정하는 이유와 함정

```
toTarget  = P_enemy - P_player          (끝점 빼기 시작점 — D2와 동일 규칙)
threshold = cos(angle / 2 * Deg2Rad)
if (Dot(aim, toTarget.normalized) < threshold) continue;
```

- **정규화 필수.** 내적이 코사인이 되려면 양쪽이 단위벡터여야 한다.
  생략하면 결과가 거리에 비례해 커져 멀리 있는 적일수록 통과한다.
  D2의 "멀리 있는 좀비가 더 빨리 온다"와 완전히 같은 구조의 실수다.
- **부등호 방향.** `Dot`은 코사인이므로 각도가 커질수록 **작아진다**(정면 1 / 90° 0 / 정반대 -1).
- **`Mathf.Abs` 불필요.** 코사인은 짝함수라 좌우 부호 정보가 이미 사라져 있다.
  붙이면 뒤쪽까지 통과해 부채꼴이 아니라 **나비넥타이 모양**이 된다.
- 실제 실수: `_threshold`에 `Mathf.Cos`를 빠뜨리고 라디안 각도만 저장했다.
  `_angle=90`이면 0.785가 들어가 실질 약 38° 부채꼴이 된다.
  **에러도 나지 않고 좀비도 죽는데 값만 조용히 틀린다.**

검증은 `_angle`을 360(threshold = -1, 전부 통과)과 1(거의 통과 없음)로 넣어 수행했다.
D2 회고의 "극단값 두 개를 손으로 넣고 따라간다"를 인스펙터로 수행한 것.

### 조준 입력을 `PlayerAim`으로 분리한 이유

방향키 입력은 무기 3종이 **모두 공통**이고, 기획서에 무기 교체(2종 택 1)가 있어 런타임에 무기가 바뀐다.
무기 안에 입력을 넣으면 같은 코드가 세 번 복사되고 교체 때마다 입력 처리가 붙었다 떨어진다.
**조준 방향은 플레이어의 상태이지 무기의 상태가 아니다.**

컨벤션 6항 기준으로도 갈린다. `MeleeWeapon`의 책임은 "주기적으로 부채꼴을 판정해 데미지를 준다"이며,
여기에 "방향키를 읽는다"가 들어가면 문장이 둘이 된다.

## 범위

- 무기는 플레이어에 **붙는 컴포넌트**로 시작한다. 자식 GameObject가 아니다.
  현재 판정 중심이 플레이어 위치와 같아 별도 Transform이 필요 없고, `transform.position`을 그대로 쓴다.
  회전 오라나 방향성 무기가 생기면 자식 오브젝트로 옮긴다(컴포넌트를 드래그 + 위치 참조 한 줄).
- `WeaponManager`는 만들지 않는다. **무기가 하나뿐인 시점에는 공통점을 알 수 없다.**
  두 번째 무기에서 판단한다.
- 입력 없을 때는 마지막 방향을 유지한다. 초기값은 `(0, -1)`(하단).
  기획서에 미기재 사항이며, `Vector2.zero`면 시작 직후 판정이 무의미해지므로 명시했다.

## 대가 (인지하고 있음)

- `OverlapCircleAll`은 호출마다 배열을 할당한다. 공격속도가 오르면 GC 압박. `NonAlloc` 계열이 개선 카드.
- 판정에 걸린 대상마다 `GetComponent<IDamageable>()`이 실행된다. 0004의 대가 항목과 같은 구조.
- 넓은 각도에서는 원형 수집 → 각도 필터가 비효율이다.
- `PlayerAim.Update`와 무기 코루틴의 실행 순서상 **조준이 한 프레임 늦게 반영될 수 있다.**
  Script Execution Order로 강제할 수 있으나 관리 비용이 크고, 약 16ms는 현재 인지 범위 밖으로 판단한다.
  "조준이 굼뜨다"는 체감이 실제로 발생하면 원인 후보로 삼는다.
- 부채꼴 시각화의 `Quaternion.Euler` 계산이 빌드에도 남는다(`Debug.DrawRay` 자체는 자동 제거됨).

## 재검토 시점

두 번째 무기(샷건 = 투사체) 구현 시. (b) 방식이 들어오면 풀링 대상이 하나 늘고,
그 시점에 무기 공통 계층과 `WeaponManager`를 함께 판단한다.
