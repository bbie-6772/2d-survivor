# 0028. 이벤트는 사건과 상태로 나누고, 갱신 방식은 변화 빈도로 정한다

- 날짜: 2026-09-05 (D9)
- 상태: 채택
- 관련: 0019(`~Screen` 부착 위치), 0022(`Health` 프로퍼티 개방), 0026(`~Screen` 접미 규칙)

## 맥락

플레이어에게 현재 상태를 알리는 UI가 전혀 없었다. 체력이 얼마 남았는지,
대시를 쓸 수 있는지 화면에서 알 방법이 없다.

붙이려는 순간 두 가지가 걸렸다.

**첫째, `Health.OnDamaged`를 재활용할 수 있는가.**
`AddMaxHealth`(0022)는 비율을 유지하므로 바의 **길이**는 변하지 않는다.
그래서 재활용이 가능해 보였으나, 표시값을 함께 띄우면 문제가 드러난다.
50/100에서 카드를 먹으면 실제로는 60/120인데 이벤트가 오지 않아 화면은 50/100에 머문다.
그리고 다음 피격에 50/100 → 50/120으로 값이 점프한다.

더 결정적으로, **`DamageFlash`가 `OnDamaged`를 구독하고 있다.**
재활용하면 카드를 먹을 때마다 플레이어가 피격당한 것처럼 빨갛게 번쩍인다.
게임이 거짓말을 하는 셈이다.

**둘째, 대시 쿨타임은 매 `FixedUpdate` 변한다.** 이벤트로 알리면 초당 50회다.

## 결정

### 이벤트를 사건과 상태로 나눈다

```csharp
public event Action OnDamaged;         // 사건 — DamageFlash가 구독
public event Action OnHealthChanged;   // 상태 — HealthBar가 구독
```

`TakeDamage`는 둘 다, `AddMaxHealth`는 `OnHealthChanged`만 발화한다.

`OnDamaged`라는 이름 자체가 근거다. **"피해를 입었다"는 사건이고
"체력이 변했다"는 상태다.** 최대치 증가는 피해가 아니다.
`GameState`/`GameOutcome`(0018), `AttackSpeed`/`_interval`(0023)에서
반복해 다룬 것과 같은 문제다.

### 갱신 방식은 변화 빈도로 정한다

> **값이 자주 변하면 프로퍼티 폴링, 드물게 변하면 이벤트.**

| 대상 | 변화 빈도 | 방식 |
|---|---|---|
| 체력 | 피격·업그레이드 시에만 | `OnHealthChanged` 이벤트 |
| 대시 쿨타임 | 매 `FixedUpdate` | `DashCooldownRemaining` 폴링 |
| 게임 타이머 | 매 프레임 | `Remaining` 폴링 (기존) |

체력을 폴링하면 값이 안 변한 대부분의 프레임에서 읽고 계산하고 대입한다.
쿨타임을 이벤트로 하면 초당 50회 발화한다. 각각 반대쪽이 낭비다.

### 이벤트는 무인자, 값은 프로퍼티로 조회

`Action<float, float>`로 싣지 않고 무인자 이벤트 + 프로퍼티 조회로 간다.

프로퍼티는 **"지금 값이 얼마냐"**, 이벤트는 **"방금 바뀌었다"** 에 답한다.
둘 다 필요한 이유는 셋째 항목에 있다.

### 초기 동기화가 필수다

**이벤트는 초기 상태를 알려주지 않는다.**
`Health.Awake`의 `_currentHealth = _maxHealth`에는 발화가 없으므로,
UI가 `Start`에서 값을 한 번 직접 읽어야 한다.
그렇지 않으면 첫 피격 전까지 바가 인스펙터 기본값으로 남는다.

구독을 먼저 걸고 그다음 동기화한다. 이벤트 기반 UI에서 흔히 빠뜨리는 지점이다.

### `DashCooldown`과 `DashCooldownRemaining` 둘 다 공개한다

0027에서 `GameTimer`는 `_duration`을 감추고 `Elapsed`만 내보냈는데,
여기서는 결론이 갈린다. 근거가 다르기 때문이다.

- `GameTimer`: 같은 뺄셈이 여러 곳에 복사될 위험이 있었다
- 대시: 나눗셈이 UI 한 곳에서만 일어나고, 두 값을 Slider의
  `maxValue`/`value`에 그대로 넣으면 **인스펙터에서 실제 초 단위가 보인다**

같은 원칙을 기계적으로 적용하지 않고 상황을 따진 결과다.
체력바도 같은 이유로 `maxValue`를 `MaxHealth`로 맞춘다.

`maxValue`를 `value`보다 **먼저** 대입해야 한다.
Slider는 `value`를 `maxValue` 범위로 clamp하므로, 순서가 반대면
최대 체력이 100→120으로 오를 때 새 값이 옛 상한에 잘린다.

### 쿨타임 바는 차오르는 방향

`_dashCooldownRemaining`은 줄어들지만 바는 차오르게 한다.
"준비됨"이 가득 찬 상태여야 직관적이다.

## 잘라낸 것

**현재 스탯 정보 표시(공격력·공격속도 등 5종).**
0022의 대가 항목대로 스탯이 세 컴포넌트에 흩어져 있어 전부 참조해야 하고,
레벨업마다 갱신이 필요하다. 얻는 것은 "숫자가 올랐다"는 확인인데
**그것은 카드를 고르는 순간 이미 안다.** 비용 대비 회수가 가장 낮다.

**공격 애니메이션.** 0017에서 이미 제외했고, 스프라이트가 캡슐 하나라 휘두를 대상이 없다.
대안으로 `MeleeWeapon.Update`가 `Debug.DrawRay`로 그리는 부채꼴을
공격 발동 순간에 짧게 표시하는 방법이 있다(애니메이터를 건드리지 않음). 여유 시 검토.

**체력·쿨타임의 숫자 표시.** 바만으로 판단 가능하다.
체력은 "몇 대 더 맞을 수 있나"를 알아야 하므로 숫자가 의미 있으나, 우선순위가 낮다.

## 보류 — 대시 로직 분리

대시를 별도 컴포넌트로 빼면 무적 상태 관리와 FSM 도입이 자연스러워진다.
0017이 FSM 트리거로 지목한 바로 그 지점이다. **그럼에도 이번에는 하지 않는다.**

- 리팩토링은 별도 커밋이어야 한다(컨벤션 4항). UI 커밋에 섞이면 축 2의 증거 가치가 떨어진다
- **드러나지 않은 결합이 있다.** `PlayerMovement.FixedUpdate`가 매 프레임
  `_rigidbody.linearVelocity`를 덮어쓴다. 대시를 분리하면 두 컴포넌트가
  같은 Rigidbody를 두고 경합한다. 현재 대시는 `position`을 직접 옮기는 순간이동이라
  충돌이 드러나지 않지만, 가속 방식으로 바꾸면 즉시 문제가 된다.
  이 조율이 분리의 실제 설계 지점이다
- D6는 풀링(축 3, 숫자로 남는 유일한 축)에 배정되어 있다

`DashCooldownRemaining` 프로퍼티는 나중에 새 컴포넌트로 따라가고
UI는 참조 대상만 바꾸면 되므로, **지금의 한 줄이 나중 리팩토링을 막지 않는다.**

## Slider 설정 주의 (D9 실측)

Slider는 Handle을 위한 여백을 갖고 태어나므로, 그대로 쓰면
`value == maxValue`인데도 Fill이 트랙 끝까지 차지 않는다.

- `Interactable` 끄기 (안 끄면 플레이어가 드래그로 체력을 조절할 수 있다)
- `Handle Slide Area` 삭제
- `Fill Area`의 Left/Right를 0으로
- **`Fill`의 Width를 0으로** ← 실제 원인이 여기였다.
  Rect Transform에 `Some values driven by Slider.` 경고가 뜨지만
  Width는 Slider의 관리 밖이라 기본값 10이 남는다

Slider를 추가할 때마다 반복되므로, 개수가 늘면 프리팹으로 저장한다.

## 재검토 시점

대시 로직 분리 시. 그 시점에 `DashCooldown` 관련 프로퍼티의 소유자가 바뀐다.
