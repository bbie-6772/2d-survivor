# 0022. 플레이어 스탯은 각 컴포넌트가 소유하고, 적용부만 한 곳에 모은다

- 날짜: 2026-09-05 (D9)
- 상태: 채택
- 관련: `plan.md` 축 4, 0017(범위), 0021(경험치)

## 맥락

레벨업 업그레이드가 공격력·공격속도·공격범위·최대체력·이동속도를 바꿔야 하는데,
이 값들이 세 컴포넌트에 흩어져 있다.

- `PlayerMovement._moveSpeed`
- `MeleeWeapon._damage` / `_attacksPerSecond` / `_radius`
- `Health._maxHealth`

후보 셋을 놓고 판단했다.

| 후보 | 구조 |
|---|---|
| **A** | 각 컴포넌트에 `AddXxx(float)` 메서드를 뚫고, 적용부가 호출 |
| B | `PlayerStats` 하나에 값을 모으고 각 컴포넌트가 거기서 읽음 |
| C | 기본값을 SO에 두고 런타임 배수를 별도 관리 |

## 결정

**A를 채택한다.**

`StatType`(enum)과 `UpgradeCard`(ScriptableObject)를 `Scripts/Data/`에 두고,
`Growth/PlayerUpgradeApplier`가 세 컴포넌트를 씬 주입으로 물어
`card.Stat`에 대한 `switch`로 해당 메서드를 호출한다.

카드 데이터는 `Assets/_Project/Data/`의 `.asset` 5종으로 둔다.
카드를 늘릴 때 **같은 `StatType`이면 코드 변경이 0줄**이고,
새 스탯이면 enum 값 + `switch` case + 대상 메서드 하나가 추가된다.

## 이유

**C는 검토 중에 전제가 무너졌다.** SO 에셋은 인스턴스가 하나뿐이라
런타임에 값을 바꾸면 에디터에서 `.asset` 파일에 그대로 저장된다.
플레이를 멈춰도 되돌아오지 않아 밸런스 데이터가 오염된다.
따라서 C는 "SO에서 읽어 런타임 홀더에 복사"가 되어야 하고,
그것은 **B에 한 겹을 더 얹은 형태**다. B보다 간단할 수 없다.

여기서 규칙 하나가 확정된다.

> **SO는 읽기 전용으로 다룬다.** 변하는 값은 SO가 아니라 런타임 객체가 소유한다.

**A와 B의 차이는 응집도와 변경량의 교환이다.**
B는 스탯이 한 곳에 모여 관리가 편하지만, 컴포넌트가 자기 행동에 필요한 값을
자기가 갖지 않게 된다. `PlayerMovement`를 다른 프로젝트에 옮기려면
`PlayerStats`가 따라와야 한다.

결정적인 것은 **마감(0017)까지의 변경량**이었다. B는 이미 동작하는 세 컴포넌트를
전부 뜯어야 하고, A는 메서드를 추가할 뿐이라 기존 동작이 깨지지 않는다.
그리고 **A → B 리팩토링은 나중에 가능하지만 그 반대는 없다.**

A가 만드는 의존(적용부가 세 컴포넌트를 앎)은 `PlayerUpgradeApplier` 한 클래스에
격리된다. 나머지 컴포넌트는 서로도, 업그레이드 시스템도 모른다.

## 함께 결정된 것

**최대 체력 증가 시 현재 체력은 비율을 유지한다.**
(50/100 → 60/120)

그대로 두면 체감이 없고, 같은 양을 더하면 회복 효과가 섞여
체력 카드가 다른 카드보다 강해진다. 비율 유지가 그 중간이다.

구현 시 **비율을 `_maxHealth` 갱신보다 먼저 계산해야 한다.**
순서를 지키지 않으면 원래 비율을 잃는다.

이를 위해 `Health`에 `MaxHealth` / `CurrentHealth` 읽기 프로퍼티와
`AddMaxHealth(float)`를 열었다. 체력 UI를 붙일 때 어차피 필요한 통로다.

## 함께 통일된 것

`AddDamage` / `AddRange` / `AddAttackSpeed` / `AddMaxHealth` 모두
**증가량이 0 이하이면 `LogWarning` 후 무시**한다.

`Health.TakeDamage`가 음수 데미지를 걸러내던 방식과 같은 수준으로 맞췄다.
디버프 카드는 이번 범위에 없으므로(0017) 감소를 허용할 이유가 없다.

## 대가

- 스탯이 여전히 세 곳에 흩어져 있어, "현재 플레이어 능력치 전체"를 한 번에
  조회할 수단이 없다. HUD에 전체 스탯을 표시하려면 세 컴포넌트를 각각 읽어야 한다.
- `PlayerUpgradeApplier`의 `switch`가 스탯 종류만큼 길어진다.
  종류가 10개를 넘으면 B로의 전환을 재검토한다.

## 재검토 시점

무기 교체(샷건 / 스나이퍼)를 구현할 때. 무기가 바뀌면 스탯의 소유자도 바뀌므로,
그 시점에 A가 유지되는지 확인한다.
