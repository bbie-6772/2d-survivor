# 0031. 오브젝트 풀링 효과 측정 — 생성/소멸 왕복 부하 조건

- 날짜: 2026-09-06 (D10)
- 상태: 채택 (측정 완료, 풀링 도입 근거 기각)
- 관련: 0030(측정 조건), 0007(despawn 콜백 주입)

## 왜 조건을 바꾸는가

0030에서 잡은 병목은 `Physics2DFixedUpdate`(밀집 상태의 접촉 해소)였고,
GC Alloc은 전 구간 0 B였다. **둘 다 풀링이 줄이는 비용이 아니다.**
풀링이 겨냥하는 것은 동시 존재 수가 아니라 **`Instantiate`/`Destroy` 왕복 횟수**이므로,
그 축에서 before/after를 비교하려면 별도의 부하 조건이 필요하다.

목표 상태: **동시 존재 수는 낮게 유지하면서 왕복 횟수를 최대화**한다.

## 측정 환경

에디터 Play / 해상도 1920x1080(Full HD) / Profiler 별도 창 / Scene 뷰 닫음 (Game 뷰 Maximize On Play)
(0030과 동일)

## 세팅 (커밋하지 않음)

| 항목 | 값 | 목적 |
|---|---|---|
| 좀비 프리팹 임시 컴포넌트 | `_TEMP_EnemyLifetime` 수명 1초 | 왕복 생성 (Health.TakeDamage로 정상 경로 사망) |
| MeleeWeapon | 비활성 | OverlapCircleAll / GetComponent 노이즈 제거 |
| Health.MaxHealth | 9999 | 플레이어 생존 |
| CardSelector | 비활성 | 스탯 고정 |
| EnemySpawner _spawnRadius | 20 (원본) | 밀집 방지 |
| WaveTable | Element 0만 유지 (Start 0 / Interval 1 / Count 20), 나머지 비움 | 스폰 조건 고정, 웨이브 전환 변수 제거 |
| Enemy↔Enemy 충돌 | ON (원본) | |
| 조작 | 무조작 | |

수명 처리는 `Invoke(nameof(Die), _lifetime)`을 사용했다.
`WaitForSeconds`는 좀비마다 새 객체를 할당하고, `Time.time` 폴링은 매 프레임 깨어나
CPU를 쓴다. 둘 다 이번 측정의 지표를 오염시킨다.

## 왕복 횟수 확보 확인

- 이론 동시 존재 수 = 초당 스폰량 × 수명 = 20 × 1 = **약 20마리**
- 초당 왕복 **약 20회**
- AliveCount가 20 근처에서 평형이면 성립, 계속 증가하면 수명 재조정
- Scene 뷰 확인: 좀비가 스폰 링 위에 흩어진 채 도달 전에 사망. 밀집 없음 → **조건 성립**

## 예상 (측정 전 작성)

- before GC Alloc: 할당 발생 프레임 1~2KB, 대부분 프레임 0B, 평균 0.5KB 내외
  - 근거: 초당 20마리 = 60fps 기준 3프레임에 1마리.
    좀비 1기당 GameObject + 컴포넌트 8종 할당을 1~2KB로 추정
- before 프레임 타임: 3차 682마리에서 2.32ms였고 이번엔 동시 20마리 수준이므로
  물리 비용은 무시 가능. **2ms 내외 예상**
- 풀링 후 예상 개선폭: GC Alloc은 0에 수렴, 프레임 타임은 유의미한 변화 없음

## 결과

### before (Instantiate/Destroy) — 초당 왕복 20회

| 프레임 | GC Alloc | CPU | UpdateScene |
|---|---|---|---|
| 20485 | 0 B | 5.60ms | 3.35ms |
| 24675 | 12.7 KB | 4.55ms | 1.99ms |
| 37813 | 464 B | 2.41ms | 0.33ms |
| 51044 | 464 B | 1.65ms | 0.20ms |
| 24844 | 70 B | 2.00ms | 0.35ms |

- 할당은 전부 `UpdateScene` 아래에서 발생. `RenderPlayModeViewCamera`는 항상 0 B
- 정상 상태 할당은 **464 B / 70 B 두 종류**
- **12.7 KB는 초반 1회만 관측되고 재현되지 않음.** 워밍업성 비용으로 보고 근거에서 제외
- Rendering 모듈: Batches 8 / SetPass 85 / Triangles 163 — 드로우콜은 문제 아님

#### 예상과의 차이

예상은 "할당 프레임 1~2KB, 3프레임에 1번"이었으나 실측은 **464 B 수준**.
좀비 1기당 1~2KB라는 모델이 틀렸다.
`Instantiate`는 대부분 Unity 네이티브 메모리에서 처리되어
**C# 관리 힙 할당(GC Alloc)으로 잡히는 양은 그중 일부**이기 때문이다.

또한 WaveTable이 `Interval 1 / Count 20`이므로 1초에 한 번 20마리가 한꺼번에 나온다.
"3프레임에 1마리"라는 예상의 전제 자체가 이 세팅에 맞지 않았다.

## 추가 실험: 풀링이 유효해지는 왕복률 찾기

### 기준

**GC 스파이크가 관측되는 순간**을 유효성의 경계로 본다.
(Profiler `GarbageCollector` 모듈에 GC 발생이 잡히고 CPU 그래프에 스파이크가 나타나는 시점)

### 설계

수명과 스폰율을 함께 조절해 **동시 존재 수는 30 내외로 고정하고 왕복률만 올린다.**
동시 존재 수 = 초당 스폰량 × 수명이므로, 스폰율을 올릴 때 수명을 같이 줄여야
밀집으로 인한 물리 비용이 섞이지 않는다.
조절 변수를 하나로 줄이기 위해 `Count`는 20으로 고정하고 `Interval`만 반씩 줄였다.

| 단계 | Interval | Count | 수명 | → 초당 왕복 | → 이론 동시 수 |
|---|---|---|---|---|---|
| 0 (기준) | 1.0 | 20 | 1.0s | 20 | 20 |
| 1 | 0.5 | 20 | 0.75s | 40 | 30 |
| 2 | 0.25 | 20 | 0.4s | 80 | 32 |
| 3 | 0.125 | 20 | 0.2s | 160 | 32 |

각 단계 30초 실행.

### 기록

| 단계 | AliveCount | GC Alloc/프레임 | GC 발생 | CPU | UpdateScene |
|---|---|---|---|---|---|
| 1 | — | 464 B | 없음 | 2.53ms | 0.32ms |
| 2 | 40 | 464 B | 없음 | 1.73ms | 0.22ms |
| 3 | 40 | 464 B | 없음 | 2.24ms | 0.54ms |

**왕복률을 2배씩 올렸는데 GC Alloc이 464 B에서 한 바이트도 움직이지 않았다.**
그리고 2단계와 3단계의 AliveCount가 둘 다 40으로 같다 —
Interval을 절반으로 줄였는데 동시 수가 늘지 않았으므로,
3단계는 2단계와 사실상 같은 조건을 다른 이름으로 잰 것이다.

### 464 B의 정체 추적

왕복률과 무관하게 값이 고정이라는 점이 이상해, **스포너를 꺼서 좀비 0마리 상태**로 측정했다.

| 조건 | GC Alloc | CPU |
|---|---|---|
| 좀비 0마리 | **464 B** | 2.23ms |

좀비가 하나도 없는데 같은 값이 찍혔다. `UpdateScene`을 펼쳐 추적한 결과:

```
UpdateScene                              464 B
└─ Update.ScriptRunDelayedTasks          464 B
   └─ UnitySynchronizationContext.ExecuteTasks   464 B (Calls 6)
```

**게임 코드가 아니라 Unity 에디터 환경의 상시 할당이다.**
즉 464 B는 배경 노이즈이며,
**좀비 왕복이 만드는 GC Alloc은 이 노이즈에 묻힐 만큼 작다.**

### 극단 조건 — 초당 2000회, 상한 해제, 8초

| 항목 | 값 |
|---|---|
| GC Alloc | **70 B** (UI 렌더 몫) |
| CPU (측정 프레임) | 1.88ms |
| 체감 | **심한 렉 발생** |

GC Alloc은 오히려 더 작게 나왔다. 반면 렉은 명확히 체감됐는데,
상한을 해제해 좀비가 무제한으로 쌓인 상태였으므로
그 렉의 정체는 왕복 비용이 아니라 **0030에서 이미 규명한 밀집 상태의 Physics2D 비용**이다.
풀에서 꺼낸 좀비도 콜라이더를 갖고 씬에 존재하므로, 이 비용은 풀링으로 줄지 않는다.

### after (풀링)

**측정하지 않음.** before 단계에서 풀링이 겨냥하는 비용이
측정 해상도 아래임이 확인되어, 비교 대상이 성립하지 않는다.

## 결론

| 가설 | 결과 |
|---|---|
| 풀링으로 GC 부담을 줄일 수 있다 | **기각** — 왕복 2000회/초에서도 GC Alloc 70 B, GC 미발생 |
| 왕복률을 올리면 효과가 드러난다 | **기각** — 20 → 160회에서 464 B 고정, 배경 노이즈였음 |
| 극단값이면 보인다 | **기각** — 대신 다른 병목(Physics2D)이 먼저 드러남 |

- **이 프로젝트의 병목은 왕복 횟수가 아니라 동시 존재 수의 물리 비용이다.**
  임계는 682~753마리(0030), 대책은 동시 스폰 상한(구현 완료).
- 실제 플레이 부하는 30~65마리로 임계의 10% 미만.
- 따라서 **현 규모에서 오브젝트 풀링을 도입할 성능적 근거는 없다.**

### 풀링이 유효해지는 조건 (미검증, 참고)

- 왕복 규모가 훨씬 큰 경우 — 수명 0.5초 투사체를 초당 수백 발 발사하는 등.
  동시 수는 적고 왕복만 많은 구조
- 프리팹이 무거운 경우 — 파티클/애니메이터/자식 오브젝트가 다수.
  현 좀비는 스프라이트 1 + 컴포넌트 8종으로 가볍다
- 모바일·저사양 타깃 — GC 스파이크가 PC에서는 묻히지만 눈에 띄는 환경
- 성능이 아니라 **상태를 유지한 채 재사용**하는 구조가 필요한 경우

이 프로젝트에서 원거리 무기(투사체)를 추가한다면 첫 번째 조건에 해당하므로,
그 시점에 재검토한다.
