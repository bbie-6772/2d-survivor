# 0007. 디스폰 호출을 콜백 주입으로 연결한다

- 날짜: 2026-08-30 (D3)
- 상태: 채택

## 맥락

`Health.OnDied`가 발행되고 있으나 구독자가 없어 좀비가 죽어도 사라지지 않았다.
누가 회수를 트리거할 것인지를 정해야 했다.

가장 단순한 답은 좀비가 스스로 `Destroy(gameObject)`를 부르는 것이다.
그러나 D6에 풀링을 도입하면 **좀비는 파괴하고 풀은 반납을 기다리는** 상태가 되어 풀이 고갈된다.
그렇다고 좀비가 스포너를 참조하면 화살표가 양방향이 된다.

## 결정

`EnemyDeath`가 `Action<GameObject>` 콜백을 주입받아 호출한다.

```csharp
// EnemyDeath
public void SetReleaseCallback(Action<GameObject> release) => _release = release;

// EnemySpawner.Setup
death.SetReleaseCallback(Despawn);   // 메서드 그룹을 그대로 전달
```

## 이유

검토한 후보는 넷이었다.

| 후보 | 문제 |
|---|---|
| 스포너가 활성 좀비 `List` 보유 | 제거 비용 + **같은 정보를 두 군데 저장**(풀이 이미 들고 있음) |
| 좀비가 스포너 참조 | 순환. 스포너 없이 생성된 좀비는 죽지 못함 |
| `IDespawner` 인터페이스로 좁히기 | 성립하지만 타입 하나를 더 만듦 |
| **`Action<GameObject>` 주입** | 좀비가 상대 타입을 전혀 모름 |

리스트 보유안을 기각한 근거가 특히 중요하다. **활성 목록은 반납 때문에 만드는 것이 아니다.**
"좀비 전체에 슬로우", "웨이브 클리어 판정" 같은 **전체 순회가 필요한 기능이 기획서에 있을 때만** 정당하며,
현재는 없다. 반납만을 위해 자료구조를 하나 더 만들면 풀과 리스트가 어긋나는 순간 버그가 된다.

콜백 주입은 좀비가 "나를 회수해줄 무언가"조차 몰라도 된다. 의존이 사실상 0이며,
0006에서 만든 `Setup`/`Cleanup` 대칭에 자연스럽게 들어간다.

## 범위

- 콜백이 `null`인 좀비(씬 배치, 테스트용, 보스 소환분)는 **경고 로그 후 반환**한다.
  `Destroy` 폴백을 두지 않는다. 폴백이 있으면 풀링 도입 후 조용히 파괴되는 개체가 생겨
  풀 고갈의 원인을 찾기 어려워진다. "죽어도 안 사라짐"이 눈에 띄는 편이 낫다.
- `Cleanup`에서 `_release`를 끊지 않는다. 재사용 시 `Setup`이 새 값을 덮어쓰므로
  끊지 않아도 자동 갱신되며, 실질적 버그를 막아주지 않는다.

## 대가 (인지하고 있음)

- `Destroy`는 즉시 파괴가 아니라 프레임 끝 예약이다. 같은 프레임에 `OnDied`가 재발행되면
  `_release`가 두 번 불릴 수 있다. **현재 유일한 방어선은 `Health._alreadyDead`다.**
- 현재 `SpawnerBase.Despawn`이 `Destroy`를 호출한다(풀링 미적용). D6에 이 한 줄만 바뀐다.

## 재검토 시점

D6 풀링 도입 시. 이 결정이 의도대로 작동했다면 `EnemyDeath`는 한 줄도 바뀌지 않아야 한다.
