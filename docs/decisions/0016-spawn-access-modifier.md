# 0016. Spawn()의 접근 제한을 protected로 좁힌다

- 날짜: 2026-09-04 (D8)
- 상태: 채택
- 관련: 0006 대가 항목 해소, `conventions.md` 5항 정밀화

## 맥락

`HeartSpawner`는 스폰 위치를 **밖에서 받아야** 하는데, 0006이 정한 훅
`protected abstract Vector2 GetSpawnPosition()`은 인자를 받지 못한다.

base에 `Spawn(Vector2)` 오버로드를 여는 안은 기각했다. base가 범용 잡동사니가 되고,
`EnemySpawner`도 쓰지 않을 오버로드를 갖게 된다. 0006이 "base가 점유한 콜백만 훅으로 연다"로
세운 절제를 여기에도 적용한다.

따라서 받은 좌표를 필드(`_pendingPosition`)에 놓고 곧바로 `Spawn()`을 부르는 형태가 되었고,
**필드에 값을 넣는 줄과 `Spawn()` 호출 사이에 다른 것이 끼면 안 된다**는 순서 의존이 생겼다.

밖에서 `Spawn()`을 직접 부르면 필드에 남아 있던 **직전 좌표**가 그대로 쓰인다.
죽인 좀비는 눈앞인데 심장이 저 멀리 뜨는 형태이며, **에러도 나지 않고 값만 조용히 틀린다.**
0010에서 `Mathf.Cos`를 빠뜨렸던 것과 같은 계열의 실수다.

## 결정

`SpawnerBase.Spawn()`을 `protected`로 좁힌다.
`HeartSpawner`는 `public void SpawnHeart(Vector2)` 하나만 열고, 그 안에서만 `Spawn()`을 호출한다.

```csharp
public void SpawnHeart(Vector2 pendingPosition)
{
    _pendingPosition = pendingPosition;
    Spawn();                 // 두 줄 사이에 아무것도 끼지 않는다
}
```

## 이유

후보 셋의 차이는 **막는 층**이다.

| 후보 | 막는 층 |
|---|---|
| **`Spawn()`을 `protected`로** | **컴파일 타임 — 애초에 부를 수 없다** |
| 좌표 유효성 플래그 필드 추가 | 런타임 — 필드가 둘로 늘고, 상태로 상태를 지키므로 어긋날 여지가 생긴다 |
| `Vector2?`로 두고 읽은 뒤 `null`로 비움 | 런타임 — 잘못 불린 **뒤에** 알아챈다 |

접근 제한만이 **버그의 존재 자체를 없앤다.** 나머지 둘은 누군가 그 경로를 실제로 밟아야
발견되므로 관찰 시점이 늦다. 조용히 틀리는 종류의 버그에서는 이 차이가 결정적이다.

이는 0006이 남긴 대가 항목 **"`Spawn()`은 public이므로 밖에서 부르면 그대로 실행된다"** 의
근본 해결이기도 하다. 가드를 추가하는 대신 통로를 닫았다.

## 함께 강제되는 것

**웨이브 매니저는 `Spawn()`을 직접 부르지 않는다.**
스포너에게 on/off와 파라미터(간격 등)만 전달하고, 스폰 호출은 스포너 자신의 코루틴이 소유한다.
"지금 10마리 뽑아" 형태의 명령을 허용하면 `Spawn()`을 다시 `public`으로 열어야 하므로 이 결정이 깨진다.

파라미터를 런타임에 바꾸려면 0008의 대가 항목이 청구된다 —
`WaitForSeconds`를 필드에 캐싱했으므로 간격 변경이 반영되지 않는다.
객체 재생성 또는 `Time.time` 기반 전환 중 하나를 웨이브 구현 시 택한다.

## 함께 정리된 것

**base가 소유한 이름을 자식이 오버로드하지 않는다.**
처음에 `HeartSpawner.Spawn(Vector2)`로 만들었더니 이름으로 base `Spawn()`을 가리는 형태가 되어
`SpawnHeart`로 되돌렸다. 0006의 CS0108 논의(자식이 base가 점유한 이름을 선언하면
경고만 뜨고 base 코드가 조용히 사라진다)와 같은 성질이며, 오버로드는 컴파일러가 아예 문제로 보지 않아
더 조용하다.

## 미해결 (D8 부채)

`Setup`에서 프리팹 구성 오류(`EnemyChase` / `EnemyDeath` 누락)를 발견했을 때
`enabled = false`만으로는 **이미 돌고 있는 `SpawnLoop` 코루틴이 멈추지 않는다.**
좀비가 계속 생성되며 `LogError`가 프레임마다 쌓인다. 필요한 것은 셋이다.

1. `StopAllCoroutines()` — 코루틴을 실제로 끊는다
2. `enabled = false` — 콜백 정지 (0009의 통일 방식)
3. 이미 생성된 개체 `Despawn(obj)` — `Destroy`가 아니라 base의 회수 경로로 되돌린다.
   D6에 풀링이 들어오면 이 한 줄이 자동으로 반납으로 바뀐다

프리팹 구성 검증의 **원래 자리는 `Setup`이 아니라 base `Awake`** 다. 스폰마다 반복 검사할 일이 아니다.
프리팹 오류는 에디터 실수이며 첫 스폰에서 즉시 드러나므로, 마감(9/7) 대비 우선순위가 낮아 미룬다.

## 함께 정밀화되는 것 (`conventions.md` 5항 / 0009)

0009는 null 대응 방식을 `Debug.LogError(메시지, this)` + `enabled = false`로 **통일**했으나,
이 문구는 코루틴을 돌리는 컴포넌트에서 부정확하다.

> **`enabled = false`가 끄는 것은 엔진이 주기적으로 호출하는 콜백뿐이다.**
> (`Update`, `FixedUpdate`, `LateUpdate` 등)
> 이미 실행 중인 코루틴은 계속 돈다. 코루틴의 진행은 엔진의 코루틴 스케줄러가 관리하고,
> 그 스케줄러가 보는 조건은 컴포넌트의 `enabled`가 아니라 **GameObject의 활성 상태**이기 때문이다.
>
> 따라서 **코루틴을 돌리는 컴포넌트를 정지시킬 때는 `StopAllCoroutines()`를 함께 호출한다.**

정지 수단 셋의 성격 정리:

| 수단 | 콜백 | 코루틴 | 범위 | 재개 |
|---|---|---|---|---|
| `enabled = false` | 정지 | **계속 돈다** | 컴포넌트 | `enabled = true` |
| `StopAllCoroutines()` | 유지 | 정지(폐기) | 컴포넌트 | `while` 처음부터 |
| `SetActive(false)` | 정지 | 정지 | **GameObject 전체** | 자동 재시작 안 됨 (`OnEnable`에서 재호출 필요) |

`SetActive(false)`는 같은 GameObject의 **다른 컴포넌트까지 함께 죽인다.**
좀비 스포너와 심장 스포너를 한 오브젝트에 붙였다면 좀비 프리팹 오류로 심장 스포너까지 멈춘다.
"이 컴포넌트가 고장났다"를 표현하려면 `StopAllCoroutines()` + `enabled = false`가 정확하다.

선택 기준은 둘이다. **끊을 범위가 컴포넌트인가 오브젝트 전체인가**, 그리고 **다시 켤 계획이 있는가.**
프리팹 오류는 다시 켤 일이 없는 확정 버그이고, 웨이브 전환의 "일반 좀비 스폰 X"는 다시 켜야 하므로
같은 수단으로 처리하려 들면 어긋난다.

## 재검토 시점

웨이브 매니저 구현 시. 매니저가 스폰 호출을 직접 필요로 하는 형태로 판명되면 이 결정을 뒤집는다.
